## 1. 总体策略

升级不是"改版本号"，是把风险切成**可以分别失败、分别回滚**的扇区。顺序不可颠倒：

```
S0 前置（分支/基线/surefire）
  └─ S1 POM 结构性清理（不改版本号也能做）
       └─ S2 依赖版本原子切换（父子版本 + 三个扇区）
            └─ S3 代码改造（Boot4/Framework7 编译与语义）
                 ├─ S4 AI 线（可后置，必须摘出构建）
                 └─ S5 BPM 线（Flowable 8）
                      └─ S6 验证与灰度
```

**两个不可动摇的前提**
1. **S2 的三个依赖扇区必须原子提交**，中间态一定 `NoSuchMethodError` / 类不匹配（详见 `03` 构建层评审）。
2. **`scm-ai` 在 S1–S3 期间摘出构建**（`scm-start/pom.xml:114` + `scm-mq-consumer/pom.xml:66` 两处），否则 Boot 3.5 与 Spring AI 2.0.1 的 Spring 6/7 冲突无法通过编译 —— 该动作需 **D2 批准**。

  验收：`mvn -pl scm-common -am compile` 通过；`@Aspect`/`@EnableAspectJAutoProxy` 行为不变（升完 S3 后随冒烟验证）。

### S3 代码改造

以"编译报错驱动"，但**必须先按 `05` 登记册改完已知 16 个 Jackson 文件 + 5 个 social 文件**，否则报错量太大无法定位。

关键语义变化（不是编译错误，但会静默改行为，必须人工核对）：
1. **Jackson 3 序列化行为变化**：日期默认 ISO-8601（不再是 epoch 毫秒）、null 写入 primitive 参数返回 400。
   ⇒ 前端时间格式、接口入参容错都会变，**必须联调**。
2. **`fastjson2` 仍是 MVC 主序列化器**（`CallbackMappingJackson2HttpMessageConverter extends FastJsonHttpMessageConverter`，`ActionInterceptorConfig.java:69` 用 `configureMessageConverters` 注册）⇒ Boot 4 里 `configureMessageConverters` 已废弃（不调用默认转换器），必须改 `extendMessageConverters`，否则 Spring AI 的 `ResponseEntity<Flux>` 流式与 swagger 会失效。
3. **Redis**：`Jackson2JsonRedisSerializer` → `JacksonJsonRedisSerializer`（Spring Data Redis 4 已把 Jackson 2 版整体 `@Deprecated(forRemoval)`）；`DefaultTyping` 从 `ObjectMapper.DefaultTyping` 迁到 `tools.jackson.databind.DefaultTyping`。**旧缓存不可回读**（D4：能否清 Redis）。
4. **Rabbit**：`Jackson2JsonMessageConverter` 4.0 起 `@Deprecated(forRemoval)` → `JacksonJsonMessageConverter`。**在途消息不可回读**（D4）。
5. **Flowable 变量**：8.0.0 依赖树里只有 Jackson 3（`tools.jackson.core:jackson-databind:3.1.7` 实证），但**存量流程变量根本不走 Jackson**——实测 1654 条 serializable 变量里 `com.fasterxml` **0 个**、`tools.jackson` **0 个**，全是 Java 原生序列化（`com.xinyirun.*` 1646 条）。
   ⇒ **升级 Jackson 3 不会弄坏流程变量**（此处早期判断方向写反，已修正）；真正的坑是老包名 `wms.Form` 导致的 `ClassNotFoundException`（D6，**与升级无关、现网现在就是坏的**）。另有 8 个 blob 内含 fastjson 类名，T2.9 顺手验。

### S5 的真实 blocker（已实测，不是推测）

Flowable 8 探针跑通只证明「代码能跑」，**没有证明「存量库能升」**。四条实测证据：

1. **引擎绑的是 baomidou 路由数据源**（`DynamicDataSourceAutoConfiguration` 的 `@Primary` 是 `DynamicRoutingDataSource`），`database-schema-update` 启动时只升级**当时路由到的那个库**（默认 master）。**启动成功 = 只升级了 master。**
2. **master 与租户库是同构双份**：`information_schema` 实测 `scm_manager` 71 张 `ACT_*`、`scm_tenant_20250519_001` 71 张，两边 `act_ge_property.schema.version` **都是 7.1.0.2** ⇒ 租户库不会被自动升级。
3. **不升级就必炸**：`flowable-engine-8.0.0.jar` 的 `HistoricProcessInstance.xml` 直接写 `STATE_`/`END_USER_ID_`（L46-47 / L233-236 / L935-938），`ActivityInstance.xml` 写 `COMPLETED_BY_`（L36/169/301）⇒ 老库上查历史即 `Unknown column`。
4. **回退不存在**：8.0.0 库上用 7.1.0 启动，实测（`R1-rollback-710-on-800-db.log:67`）`FlowableException: Could not update Flowable database schema: unknown version from database: '8.0.0.0'`。

**处置**：`database-schema-update=false` + 逐库手工 DDL + 升级前备份 + 恢复演练。
**库数量 = 1（master）+ `s_tenant_manager` 记录数**：本机 dev 实测只 1 条租户（`scm_tenant_20250519_001`），生产按真实条数算，**每多一个租户就多一次 DDL + 一次备份 + 一次回读验证**。
